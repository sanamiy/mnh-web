形式検証のしくみと限界

形式検証の道具は、それぞれ違う方法で「すべての場合」を調べます。このページでは、まず方式ごとのしくみを説明し、そのしくみから、どこまで検証できてどこから検証できないのかを整理します。

全体像：形式検証で何ができるか

形式検証とは

形式検証は、プログラムや設計が、数学的に書いた性質を満たすかどうかを、定めた範囲のすべての場合について機械で調べる技術です。

テストは、選んだ入力で動作を確かめます。形式検証では、調べる入力や動作の範囲と、守るべき性質を明記して、その範囲全体について調べます。論理式を解く、到達できる状態をたどる、一般的な証明を書くなど、範囲全体を扱う方法は方式によって違います。性質を破る具体例は反例と呼びます。

形式検証には、必ず検証対象が必要です。動いているプログラム、ファイアウォールの設定、通信の手順など、調べる対象があって初めて意味を持ちます。そして「すべての場合」とは、世の中のすべてではなく、対象と性質を書いた範囲のすべてです。この範囲の外は何も分かりません。

5種類の検証方式

このページでは、代表的な5つの進め方を比べます。違うのは、入力や動作の範囲全体について、何を根拠に「性質が成り立つ」と言うかです。これらは完全に別々の分類ではなく、1つの道具が複数の方法を組み合わせることもあります。

「すべての場合」を扱う、とは

たとえば、数学上の整数を使う計算 y = x + 1 について、「x が0以上なら、結果の y は必ず x より大きい」と確かめたいとします。ここでは、桁数に上限のあるプログラムの整数は考えません。

x = 0、1、100 を試すのはテストです。一方、式を使う方法では、x の値を決めないまま、次の条件を一緒に渡します。

前提：x >= 0
動作：y = x + 1
起きてほしくないこと：y <= x

この3つを同時に満たす整数 x, y はあるか？

この例では、y = x + 1 と y <= x が両立しないので、答えは「ない」です。特定の値で成功したのではなく、前提に合うどの整数を入れても、性質を破れないことが分かります。これは説明用の簡単な例で、複雑な式では判定できないこともあります。

「式にする」とは、このように値を未確定の変数にし、動作と条件を等式・不等式などで表すことです。「全入力を長い一覧に書く」という意味ではありません。複数の値に共通する関係を、式のまま調べます。

ただし、5方式すべてが「1つの式を解く」わけではありません有界モデル検査は範囲内の動作を式にまとめ、記号実行は経路ごとに式を作ります。TLCは状態を列挙し、演繹的検証は部分ごとの証明問題を作り、証明支援系は書かれた証明を検算します。
方式範囲全体を扱う方法向いている対象道具の例
有界モデル検査指定範囲の動作を1つの論理式にまとめる既存の C コードCBMC
記号実行実行経路ごとに、そこに入る入力の条件を式にする既存の Python コードCrossHair
状態空間の全探索有限のモデルで、到達できる状態を列挙する並行処理、通信手順の設計TLA+（TLC）
演繹的検証注釈を使い、部分ごとの証明問題に分ける仕様と一緒に書くコードDafny, Verus
証明支援系任意の入力に通用する証明を書いて検算する数学、コンパイラや OS の中核Lean, Isabelle, Coq

① 有界モデル検査：範囲を決め、動作をまとめて式にする

渡すもの：実際のコード、守りたい性質、ループなどをどこまで展開するかの上限です。CBMCなら、Cのコードに「配列の外を読まないか」などを検査させられます。

調べ方：ループを指定回数分の処理に置き換え、代入や分岐の関係を論理式にします。入力の値は未確定のままです。「この範囲の動作で、性質を破る入力はあるか」を解くので、上限が3回だから入力を3個だけ試す、という意味ではありません。

分かること：検査を完了して反例がなければ、モデル化された指定範囲では性質が成り立ちます。ただし、その先のループは別問題です。ループが上限内で終わることも確認できれば、そのループの範囲外が残っていないと言えます。図とコードで詳しく見る。

しくみの出典：CBMC公式

② 記号実行：値を決めず、分岐ごとに道をたどる

渡すもの：関数のコードと、入力の条件・結果の性質です。CrossHairなら、Pythonの関数に契約を書いて渡します。

調べ方：たとえば絶対値を返す関数なら、x >= 0 の経路と x < 0 の経路に分けます。前者の結果は x、後者の結果は -x です。各経路の条件に「結果が負になる」を足して、両立する入力を探します。1つの経路の式が、多数の入力をまとめて表します。

分かること：負の経路で誤って x をそのまま返していたら、x = -1 のような反例を作れます。一方、分岐やループが増えると経路が増え、調べ切れなくなります。反例なしで時間切れになっても、全入力について正しいとは言えません。実行のしくみを詳しく見る。

しくみの出典：CrossHair公式の実装解説

③ 状態空間の全探索：起こりうる状態の地図を作る

渡すもの：初期状態、起こりうる操作、守りたい性質を記述したモデルです。TLA+で設計を書き、TLCで調べる場合が代表例です。

調べ方：たとえば「残席1に対して2人が予約する」設計なら、残席数や各人の処理段階を状態にします。残席確認と予約確定を別々の操作にすると、「Aが確認→Bが確認→Aが確定→Bが確定」の順序も探索対象です。TLCは、有限にしたモデルで到達可能な状態を列挙し、「予約済み人数は定員以下」のような条件を確認します。

分かること：二重予約の状態に届けば、そこまでの操作列が反例になります。全探索を完了できれば、そのモデルについて確認できます。ただし、モデルに書いていない操作や、実装コードがモデルどおりかは別に確かめる必要があります。状態遷移の図で詳しく見る。

しくみの出典：TLA+の解説書・TLCの章

④ 演繹的検証：全実行の代わりに、部分ごとの証明をつなぐ

渡すもの：コードと、「呼ぶ前の条件」「返した後の条件」「ループの各周で保つ条件」などの注釈です。DafnyやVerusがこの方法を使います。

調べ方：たとえば1からnまで足すループで、「iまで進んだ時点で、合計sは1からiまでの和」という不変条件を書きます。道具は、開始時に成り立つか、任意の1周で保たれるか、終了時に欲しい結果を導けるかを証明問題にします。任意の1周について保たれると示すことで、回数を一つずつ展開せずに済みます。

分かること：各証明が通れば、書いた前提とモデルの下で結果の性質を保証できます。処理が必ず終わることには、終了を示す条件も必要です。失敗しても、バグとは限らず、不変条件や補助の証明が足りない場合があります。不変条件とコードを詳しく見る。

しくみの出典：Dafny公式・ループ不変条件

⑤ 証明支援系：一般的な証明を書き、その証明を検算する

渡すもの：数学的に定義した対象、証明したい命題、その証明です。Leanでは、人やAIが書いた証明や、自動化機能が作った証明を、小さな検査器である「核」が確認します。

調べ方：たとえば「どんな自然数nでも、nに0を足すとnになる」という命題なら、nを一つずつ試すのではなく、定義や帰納法などを使って任意のnに通用する証明を書きます。核は、証明の各段階が定義・公理・推論規則に従っているかを検算します。入力の全探索とは違います。

分かること：確認できるのは、採用した定義や公理から、その命題が導けることです。「整列結果が昇順」しか証明しなければ、「元の要素がすべて残る」までは保証しません。何を命題にするかと、実物のコードとの対応は、人が確認します。核と証明の例を詳しく見る。

しくみの出典：Lean言語リファレンス

コードにせず、設定や制御則を直接論理式に書いて Z3 に解かせる使い方もよくあります。AWS の権限ポリシーの検査が代表例です。また、ニューラルネットには専用の検証器があります。これらは後半で説明します。

最初の1回

割り勘の関数に、CrossHair で性質を付けます。pre が入力の条件、post が守られるべき性質です。

def split(total: int, n: int) -> int:
    """
    pre: total > 0 and n > 0
    post: __return__ * n == total
    """
    return total // n
$ crosshair check --analysis_kind=PEP316 split.py
split.py:4: error: false when calling split(1, 2) (which returns 0)

1円を2人で割ると、1人0円になって1円消える、という反例が出ました。入力を自分で選んでいないことが重要です。

結果の読み方

「エラーが出なかった」は、「正しい」とは限りません。何を調べ終えたのかは、道具ごとの表示で確かめます。

表示意味言えること
Z3：unsat性質の否定を満たす値がない書いた式の範囲では証明済み
Z3：sat性質を破る値がある反例あり
Z3：unknown判定できなかった何も言えない
CrossHair：出力なし時間内に反例が出なかった何も言えない
CrossHair：Confirmed over all paths全経路を調べ切った（--report_all で表示）与えた入力条件の範囲で成立
CBMC：VERIFICATION SUCCESSFUL指定した展開回数までは反例なし--unwinding-assertions なしでは範囲の外は不明
TLC：No error has been foundモデルの全状態で性質が成立モデルの範囲で成立。コードの話ではない
Dafny：might not hold証明できなかったバグとは限らない。補助の注釈が足りないこともある

反例が出なかったときは、調べ切ったのか、途中で打ち切ったのかで意味が変わります。調べ切って「ない」なら証明です。打ち切ったなら判定不能です。表の unsat と Confirmed over all paths が前者で、unknown と「出力なし」が後者です。

反例は必ず見つかるのか

必ずではありません。見つかるのは、性質を式に書けて、探索が届く範囲のバグです。次の2つの関数は同じ値を返すので、どちらも入力 4321 で性質を破ります。

def direct(n: int) -> int:
    """
    pre: 0 <= n <= 5000
    post: __return__ != 4321
    """
    return n

def counted(n: int) -> int:          # 性質は direct と同じ
    c = 0
    for _ in range(n):
        c += 1
    return c

手元の実験（CrossHair、1条件60秒）

direct   → error: false when calling direct(4321)
counted  → Not confirmed（見逃し）

ループを挟むだけで見逃しました。ハッシュ値で分岐する関数でも、100万通りの入力に反例が23個あるのに、見つかりませんでした。また、TLA+ の反例は書いたモデル上の手順で、実物のコードに同じバグがあることまでは示しません。性質が弱ければ、バグがあっても通ります（全方式に共通する限界）。

しくみを深掘り

充足可能性判定：多くの道具の土台

「性質が成り立つ」を「反例がない」に言い換える

プログラムの動作を式 P、性質を式 Q とします。「P ならば必ず Q」を証明する代わりに、次の式を満たす値を探します。

P∧¬Q

動作としてはありうるのに性質を破る、という意味の式です。値が見つかれば、それが反例です。どの値でも無理だと分かれば、反例はないので、性質はすべての場合で成り立ちます。証明の問題が、反例を探し切る問題に変わります。

SAT：式を真にできる値があるかを調べる

SAT は、「真か偽の変数でできた式を、真にできる値はあるか」を問う問題です。性質の真偽を直接調べるのではありません。性質を破る状況を式にして渡し、値があれば反例、値がなければ性質はいつでも成り立つ、と読みます。

小さな例で見ます。次のプログラムで、性質は成り立つでしょうか。

動作1：会員なら割引する
動作2：割引したらログを残す
性質 ：会員ならログが残る

性質を破る状況は「会員なのにログがない」です。これが起こりうるかを、順に埋めて調べます。

手順根拠分かること
1性質を破る状況会員＝真、ログ＝偽
2動作1割引＝真
3動作2ログ＝真。手順1と矛盾

どの手順も、そうなるしかない値を書いただけです。それでも矛盾したので、どんな値でも「会員なのにログがない」状況は作れません。つまり、性質は成り立ちます。変数3個の8通りを全部確かめても、結果は同じです。

動作2 がなければ、矛盾は起きません。会員＝真、割引＝真、ログ＝偽で式が真になり、これが「会員なのにログがない」という反例です。

順に埋められないときは、場合分けする

値が1つに決まらないときは、仮に決めて進みます。たとえば、次の4つの条件を同時に満たす値を探します。

a なら b
a なら b でない
a でないなら c
a でないなら c でない

a は真か偽のどちらかしかないので、両方で矛盾すれば、どの値でも無理です。数学の場合分けの証明と同じ理屈です。こうして全部の可能性がつぶれれば「解なし」、途中で全変数が矛盾なく決まれば「解あり」です。

全通りを試さずに済む理由

変数が n 個なら、組み合わせは 2n 通りあります。変数が増えると、1つずつは試せません。そこで使う手法が矛盾からの学習（CDCL）です。この手法を実装した道具に CaDiCaL などがあります。

矛盾が起きたら、原因を「x と y を同時に真にはできない」のような新しい条件として覚えます。この2つが原因なら、ほかの変数がどんな値でも同じ矛盾が起きるので、該当する候補をまとめて調べずに済みます。

SMT：数や文字列の意味を足す

SAT の変数は真か偽だけですが、プログラムには整数、配列、文字列が出てきます。問いをそこまで広げて、「整数や文字列なども含む式を、真にできる値はあるか」としたものが SMT です。解くときは、式の骨組みを SAT と同じ手法で解きながら、x>3 と x<2 が両立しないといった中身の判断を、数や文字列の専門の解法に任せます。この SMT を解く代表的な道具が Z3 です。CrossHair、Dafny、SMTChecker の裏側でも使われています。

固定長の整数は、1ビットずつの真偽の式に展開して SAT で解くこともできます。C の int のオーバーフローまで正確に扱えるのは、このためです。

有界モデル検査：ループを N 回分の式に開く

CBMC のしくみです。プログラムのループを指定回数だけ展開し、代入を式に変えて、全体を1つの論理式にします。反例を探す部分は SAT に任せます。

入力は未知のまま式に入るので、N 回以内に起きるバグは入力に関係なくすべて見つかります。一方で、N 回を超えた先は式に入っていません。CBMC は、ループが N 回で本当に終わることを確かめる展開確認（unwinding assertion）を用意しています。

単体テストとの違い

単体テストは、人が選んだ値を入力して実行し、結果を見ます。有界モデル検査は、入力を値を決めないまま式にして、「assert を破る値はあるか」を解きます。試した値の中から探すのではなく、式から破る値を求めます。

int discount(int price) {
  if (price == 123456) return -1;  // バグ
  return price;
}

int p = nondet_int();              // 値を決めない
__CPROVER_assume(p >= 0);
assert(discount(p) >= 0);

入力に 0、100、9999 を与える単体テストは、すべて通ります。同じ関数を CBMC にかけると、p=123456 という反例がすぐに出ます。int の値を1つずつ試したわけではありません。

N はループの回数で、入力の個数ではありません。この例にはループがないので、回数の制限は関係せず、0 以上の int のすべてを調べたことになります。

単体テスト有界モデル検査
入力人が選んだ値値を決めず、すべて
調べ方実行して結果を見る式にして解く
通ったときに言えること選んだ値では動いたループ N 回以内なら、どの入力でも assert は破れない

範囲の外を保証しないので、証明の方式としては弱い方です。それでも、選んだ値しか試さない単体テストよりずっと広く調べられ、コードをほぼそのまま渡せます。手元の自販機のバグは、N を増やしていくと8回の展開で見つかりました。また、ループの回数に上限があるコードなら、範囲の外が残らないことも確かめられ、その場合は証明になります（有界モデル検査の限界）。

記号実行：入力を記号のまま走らせる

CrossHair のしくみです。入力に具体的な値を入れず、記号のまま実行します。if に出会うたびに、どちらへ進むための条件を集め、Z3 に「この道に入る入力はあるか」を尋ねます。

経路の数が有限で、すべて調べ切れれば、全入力についての確認になります。この場合に CrossHair は Confirmed over all paths と表示します。経路が多すぎて調べ切れないときは、見つかった反例を返すだけです。分岐が増えるほど経路は倍々に増えるので、記号実行は反例探しに強く、証明には向かないことが多い方式です。

CrossHair は、コードを Python の上で実際に実行します。解析ではなく実行なので、既存のコードにそのまま使えます。純粋な関数でなくても構いません。手元の実験では、引数、オブジェクト、グローバル変数を書き換える関数でも反例が出ました。一方、ファイルへの書き込みのように外へ影響する処理は、CrossHair が安全のために止めるので、その関数の検査は中断します。外とのやり取りを計算の部分から切り分ければ、計算の部分は検査できます。

状態空間の全探索：設計を全部たどる

TLA+ で設計を書き、検査器 TLC で調べます。ここで書くのはコードではなく、システムの状態（変数の値）と、起こりうる遷移の定義です。TLC は初期状態から幅優先で、到達できる状態をすべて訪ねます。

TLC は、訪問済みの状態を丸ごと保存せず、64ビットの指紋（ハッシュ値）だけを保存して記憶を節約します。そのため、別の状態が同じ指紋になると調べ漏らす可能性があり、実行後にその確率の見積もりを表示します。

調べられる性質は2種類あります。安全性は「悪いことが起きない」という性質です。たとえば「二重請求は起きない」なら、二重請求に至る手順が1つ見つかれば反例になります。活性は「良いことがいつか必ず起きる」という性質です。たとえば「申請にはいつか必ず結果が出る」なら、結果が出ないまま永遠に待ち続ける手順が反例になります。

演繹的検証：注釈から証明すべき式を作る

Dafny のしくみです。全体をたどる代わりに、関数の入口と出口の条件を書き、部分ごとに証明します。その土台が、次のホーア三つ組です。

{P}C{Q}

「条件 P が成り立つときに処理 C を実行し、終わると、必ず条件 Q が成り立つ」という意味です。Dafny はコードと注釈から、証明すべき論理式を自動で作り、Boogie という中間言語を通して Z3 に解かせます。

難しいのはループです。何回回るか分からないループを、展開せずに扱うために、人が不変条件を書きます。「毎周の前後で保たれる条件」を示せれば、回数によらず成り立ちます。これは数学的帰納法と同じ構造です。止まることは、周回ごとに必ず減る量（decreases）で示します。

method Sum(n: nat) returns (s: nat)
  ensures s == n * (n + 1) / 2
{
  s := 0;
  var i := 0;
  while i < n
    invariant i <= n && s == i * (i + 1) / 2  // 毎周保たれる
    decreases n - i                           // 必ず減る
  { i := i + 1; s := s + i; }
}

有界モデル検査と違い、回数に上限がありません。代わりに、不変条件を考える仕事が人（または AI）に移ります。Solidity の SMTChecker が使うホーン節解法（CHC）は、この不変条件を解法側で自動的に探す方式です。

証明支援系：証明そのものを検算する

Lean、Isabelle、Coq などです。ここまでの方式は探索で答えを探しましたが、証明支援系では証明そのものをデータとして書き、それが正しいかを検査します。

Lean の土台にあるのは、命題を型、証明をその型の値として扱う対応です（カリー・ハワード対応）。「証明が正しいか」は「この値の型が合っているか」に置き換わるので、型検査器で判定できます。証明を探すのは難しくても、できた証明を検算するのは機械的にできます。

信じる対象を小さな核に絞れるのが最大の強みです。

なぜ機械で検算できるのか

証明は、推論の規則を1段ずつ適用した列です。検算では、各段が規則に合っているかを順に照合するだけです。数独を解くのは大変でも、解答の確認はすぐできるのと同じで、証明を見つけるのは難しくても、確かめるのは機械的にできます。

theorem swap (p q : Prop) (h : p ∧ q) : q ∧ p := ⟨h.2, h.1⟩

「p かつ q なら、q かつ p」という命題が型で、:= の右の値がその証明です。自動証明の命令で書いても、できあがるのは同じ種類の値で、核はその値を検算します。

核は本当に偽の証明を止めるのか

手元の実験（Lean 4.35）

試したこと結果
正しい証明通過
2 + 2 = 5 を証明したと主張する拒否
左右を取り違えた証明拒否
証明生成の層を飛ばして、False の偽の証明を核へ直接渡す核が拒否。ファイル全体が失敗し、成果物も作られない
sorry で証明を省く通るが警告が出る。#print axioms に sorryAx と出る

検算が保証しないこと

核が保証するのは「定理文のとおりに証明されている」ことだけです。定理文が弱いと、次のように警告なしで通ります。

def mySort (_ : List Nat) : List Nat := []   -- 常に空リストを返す

theorem mySort_sorted (l : List Nat) :
    (mySort l).Pairwise (· ≤ ·) := by simp [mySort]

「結果は整列済み」は正しく証明されました。しかし、元の要素が残ることを定理文に書いていないので、何も防げません。定理文が欲しい性質かどうかは、人が読んで判断します。

AI が証明を書けるなら、Lean が最強か

確実さでは最強の候補です。Lean の最大の弱点は人手のコストで、AI はそこを埋めます。しかも AI の証明が間違っていても核が弾くので、AI を信じなくて済みます。ただし、次の2つは残ります。

  • 定理文：AI が弱い定理にすり替えても通ります。証明が安くなるほど、人が読む定理文が増えます
  • 実物のコードとの距離：証明の対象は Lean 上の定義で、動いている C や Python ではありません

そのため、Lean は数学や新しく作る中核部分に向きます。動いているコードのバグ探しには、コードをそのまま渡せて、反例が修正の手がかりになる CBMC や CrossHair のほうが向きます。

分担AI が証明を書き、核が検算し、人は定理文を読みます。

ニューラルネットの検証：折れ線の場合分け

ReLU を使うネットは、入力に対する折れ線（区分線形）の関数です。この形を利用して、「性質を破る入力はあるか」を解きます。

何を検証するのか

調べるのは、「入力がこの範囲なら、出力はこの条件を満たす」という形の性質です。代表例は画像分類の頑健性です。基準の画像 x0 の各画素を最大 ε だけ変えても、正解クラス c の得点がほかのクラス j を上回り続ける、という性質を次のように書きます。

∀x:‖x−x0‖∞≤ε⇒fc(x)>fj(x)

破る値が見つかれば、それが誤分類を起こす入力（敵対的サンプル）です。なければ、その範囲に誤分類を起こす入力はありません。保証されるのは選んだ x0 のまわりだけで、ほかの画像については何も言えません。

ReLU で場合分けする

ReLU は「入力が正ならそのまま、負なら0」です。各 ReLU がどちらの側にいるかを決めると、ネット全体が線形の式になり、線形の不等式として確実に解けます。ただし、場合の数は ReLU が n 個で最大 2n 通りです。

緩い見積もりで、場合分けを省く

そこで専用の検証器は、まず入力の範囲を層ごとに伝えて、出力の上下限を素早く見積もります。これが境界の伝播です。見積もりは実際より広くなりますが、実際の範囲を必ず含むので、見積もりの範囲で性質が成り立てば証明になります。

最小の例で見ます。次のネットの値は実際には |x| で、最大は 1 です。「y≤1.5」を確かめます。

y=ReLU(x)+ReLU(−x),−1≤x≤1
手順分かること結果
境界の伝播各 ReLU は 0 以上 1 以下なので、y は 0 以上 2 以下上限 2 では言えない
x≥0 の場合y=x なので y≤1成立
x<0 の場合y=−x なので y≤1成立

境界の伝播は2つの ReLU を別々に見るので、同時には最大にならないことが分かりません。このように見積もりで言えないときだけ、ReLU を1つ場合分けして見積もりを締めます。これが分枝限定法です。見積もりで決着した枝は、それ以上調べずに済みます。

α,β-CROWN は、この見積もりを GPU で高速に行う検証器です。場合分けの条件を調整用の変数 β で見積もりに組み込み、勾配法で β を調整して見積もりを締めます。論文は、線形計画法を使う従来の分枝限定法より最大で3桁速いと報告しています（Wang ら、2021）。ネット検証の競技会 VNN-COMP の2021年の優勝ツールです。

実例と、規模の壁

Reluplex の論文は、無人航空機の衝突回避システム ACAS Xu の試作ネット45個（各300個の ReLU）を検証しました。性質 φ1 は41個で証明でき、4個は時間切れでした。性質 φ2 は35個で反例が見つかり、調査の結果、許容できる動作と判断されました。つまり、反例がそのまま欠陥とは限らず、人の判断が残ります。

汎用の解法では、この規模でも苦戦します。同論文の比較では、2個のネットの8問に4時間の制限で挑み、SMT の解法で解けたのは Yices と MathSAT の2問ずつでした。Reluplex は8問すべて解いています。手元の実験でも、隠れ層1層のランダムなネットを Z3 に渡すと、ReLU 40個は1.44秒で解けましたが、80個では60秒以内に決着しませんでした（各1回の小さな実験です）。

限界：どこまで検証できるのか

実装・設計上の限界（方式別）

各方式の限界は、しくみからそのまま出てきます。この節の「手元の実験」は、ハッカソン用の小さな検証コードで確認した実際の結果です。

SAT / SMT：解けない式と、不安定さ

SMT の解法は、理論ごとに得意不得意があります。Z3 の公式文書は、非線形の実数算術について「Z3 は完全ではなく、unknown を返すか、止まらないことがある」と明記しています。掛け算どうしの式が入ると、急に難しくなります。

手元の実験（Z3、制限時間20秒）

x*x*x + y*y*y == z*z*z, x,y,z > 0（整数）  → unknown（時間切れ）
a*a + b*b < 1, a + b > 2（実数）           → unsat

もう1つの問題が不安定さです。意味の変わらない変更でも、解法の探索が変わって通らなくなることがあります。6つの検証プロジェクトの 17,043 問を調べた研究では、最新版の解法で 2.6% の問題が不安定で、プロジェクトによっては 5.0% に達しました。解法の更新で、かえって不安定になることも多いと報告されています。

有界モデル検査：範囲外は「成功」と出る

N 回を超えるバグは、式に入っていないので見つかりません。しかも、表示は成功になります。

手元の実験（CBMC 5.95、バグを入れた自販機のコード）

$ cbmc vending.c --unwind 3
**** WARNING: Use --unwinding-assertions to obtain sound verification results
VERIFICATION SUCCESSFUL       ← バグがあるのに成功

$ cbmc vending.c --unwind 3 --unwinding-assertions
[main.unwind.0] unwinding assertion loop 0: FAILURE
VERIFICATION FAILED           ← 展開が足りないことが分かる

また、CBMC はプログラムの中しか見ません。ファイル、ネットワーク、OS の動作など、外の世界は人が模型を書くか、任意の値として扱う必要があります。

記号実行：経路爆発と、副作用

分岐を1つ通るごとに経路は最大2倍になります。ループの回数が入力で決まる場合は、経路が無数にあることもあります。CrossHair の公式文書の限界の節は、最初に「反例がないことは、性質が成り立つ保証ではない」と書いています。

ほかにも、同じ入力で動作が変わるコードは、基本的に解析できません。乱数のように CrossHair が値を差し替えられるものは例外で、手元の実験では乱数が6を返す場合の反例も出ました。また、コードを実際に実行するので、ディスクやネットワークへの保護はあっても完全ではなく、C で書かれた拡張の動作は防げません。

状態空間の全探索：状態爆発と、コードとの差

状態の数は、プロセスや変数が増えるほど掛け算で増えます。実際のシステムは無限の状態を持つことも多いので、「サーバー3台、メッセージ4通まで」のように有限の模型に縮めて調べます。範囲外の台数で起きるバグは見つかりません。

より本質的なのは、検証したのが設計であってコードではないことです。AWS は TLA+ で、最短でも35手かかるバグを発見した一方で、実行コードが仕様どおりかを検証できる、大規模分散システムに使える道具は知らないと述べています。

指紋の衝突も理論上はありえますが、手元の実験では TLC が見積もった確率は 9.8×10−19 で、小さなモデルでは問題になりません。

演繹的検証：正しくても通らない

Dafny のエラーは「バグがある」ではなく「証明できなかった」という意味です。不変条件が足りないのか、本当にバグなのかは、人が切り分ける必要があります。

Dafny の公式文書は、小さく正しい変更で証明が時間切れになる現象を脆さ（brittleness）と呼び、自動推論の決定可能性の限界に根本原因があると説明しています。また、assume や {:axiom} で証明を省くと、書いた内容が間違っていた場合に、「証明した」という答えが信用できなくなります。

証明支援系：コスト

もっとも強い保証を得られますが、高くつきます。OS のマイクロカーネル seL4 の検証では、C コード 8,700 行に対して、証明は Isabelle で 200,000 行、労力は約20人年でした。

証明支援系でも、抜け道は残ります。Lean の sorry は証明の省略で、独自の公理を足すこともできます。計算で済ませる native_decide は、核だけでなくコード生成器も信じることになります。#print axioms で、定理が依存する公理を確認してください。

ニューラルネット：規模と意味

ReLU ネットの性質の検証は NP 完全であることが証明されています（Katz ら、2017）。つまり、最悪の場合は指数時間を覚悟する必要があります。同論文の検証対象は、隠れ層に合計300個の ReLU を持つネットでした。専用検証器の進歩で扱える規模は広がっていますが、現在の大規模な言語モデルの全体を証明する方法にはなっていません。

規模より難しいのは性質です。「入力の数値を少し変えても出力が大きく変わらない」は書けますが、「この回答は事実として正しい」「この文章は親切だ」は、そもそも式に書けません。

全方式に共通する限界

どの方式でも、証明が言えるのは「前提が正しければ、書いた性質が、書いたモデルで成り立つ」ということだけです。下の4か所は、証明の外にあります。

① 性質が弱いと、ダメな実装も通る

もっとも起きやすい失敗です。検査器は書かれた性質しか調べません。

手元の実験（CrossHair）

def checkout(price, percent, fixed):
    """
    pre: price >= 0 and 0 <= percent <= 100 and fixed >= 0
    post: 0 <= __return__ <= price
    """
    return 0     # 何を買っても無料

→ Confirmed over all paths.

0 ≤ 請求額 ≤ 定価 は安全性なので、何も請求しない実装でも通ります。「割引を正しく反映した額である」まで書く必要があります。TLA+ でも同じで、「請求は1回まで」だけなら、一度も請求しないシステムが通ります。安全性に、活性や機能の性質を組み合わせてください。

前提が強すぎる場合も同じです。手元の実験で、Solidity のトークンの初期残高を入れ忘れたところ、全員の残高が0のままなのでバグの経路に到達できず、バグがある版まで安全と判定されました。

② モデルは現実そのものではない

Smith（1985）は、証明が示すのは2つの形式的な記述の間の整合性（相対的な無矛盾性）であり、機械と現実の世界の関係ではない、と指摘しました。モデルに書かなかった現象（停電、遅延、人の操作ミス）は、検証の対象になりません。

③④ 検証された部分の外でバグが起きる

Fonseca ら（2017）は、検証済みの分散システム3つ（IronFleet、Verdi、Chapar）を調べ、16個のバグを発見しました。原因は、仕様、検証と外部をつなぐ薄い層、検証の補助ツールなど、検証された部分とそれ以外の境界にありました。一方で、8か月以上かけて探しても、検証された分散プロトコル自体のバグは見つかりませんでした。

Yang ら（2011）も同じ構図を示しました。ランダムなプログラムで主要な C コンパイラをテストしたところ、検証済みコンパイラ CompCert の証明部分からは、他のコンパイラで見つかった種類のバグが見つかりませんでした。約6 CPU 年を費やしても、です。ただし、証明していない部分からはバグが見つかりました。

seL4 の検証も、コンパイラ、アセンブリ、ハードウェアの正しさを前提にしています。

つまり形式検証は、証明した部分にはとても強く効きます。そして、証明の外側が残ります。テストの代わりではなく、テストと組み合わせて使うものです。

理論上の限界

ここまでの限界は、道具の改良で押し戻せるものもありました。ここからは、どんなに道具が進歩しても越えられない限界です。

停止性問題：万能の判定器は作れない

チューリング（1936）に由来する結果です。「任意のプログラムと入力を受け取り、そのプログラムが止まるかどうかを必ず正しく答える」アルゴリズムは存在しません。

証明の考え方は、自己言及です。そのような判定器 halts があると仮定し、次のプログラムを作ります。

def trouble(p):
    if halts(p, p):      # p に p を渡すと止まるなら
        while True: pass # 永久に回る
    else:                # 止まらないなら
        return           # すぐ止まる

trouble(trouble) は、止まると判定されたら止まらず、止まらないと判定されたら止まります。どちらの答えも間違いになるので、halts は存在できません。

ライスの定理：動作に関する性質はすべて同じ

ライス（1953）は、これを一般化しました。プログラムの動作に関する非自明な性質は、すべて決定不能です。決定不能とは、どの入力にも正しく答えて必ず止まるアルゴリズムが存在しない、という意味です。非自明とは、満たすプログラムと満たさないプログラムの両方がある、という意味です。「配列の範囲外を読まない」も「秘密を漏らさない」も、ここに含まれます。

だから、どの道具も何かを諦めている

チューリング完全な言語を相手にする自動検査器は、次の3つを同時に満たせません。

道具諦めたもの具体的には
CBMC範囲指定した回数までに問題を制限して、答えを出す
TLC範囲有限のモデルに制限して、全探索する
CrossHair完全性時間内に調べ切れなければ、何も断定しない
Dafny完全性正しくても「証明できない」と答えることがある
SMTChecker完全性公式文書のとおり、健全だが不完全で、誤報がありうる
Lean自動化証明は人や AI が書き、機械は検算だけする
誤解しやすい点決定不能とは「すべてのプログラムに使える1つの手順がない」という意味で、「検証できない」という意味ではありません。個別のプログラムには個別の証明が書けます。seL4 も、その1つです。また、実際の計算機は有限なので原理上は全探索できますが、状態数が膨大で現実には終わりません。そこに次の計算量の壁があります。

セキュリティホールがないことは検証できるか

ライスの定理が否定するのは、どんなプログラムにも使えて、必ず止まり、必ず正しく答える検証器だけです。実用の検証器は「分からない」と答えることで、これを避けます。Rust のコンパイラが身近な例で、unsafe を除けば通ったコードはメモリ安全です。その代わり、安全でも拒否されるコードがあります。個別のプログラムなら証明もできます。seL4 は、仕様どおりに動き、クラッシュせず、危険な操作もしないことを証明しました。

本当の壁は、ライスの定理より性質を式に書けるかどうかです。

確かめたいこと検証理由
バッファオーバーフローがないできる式に書ける
権限のない人が読めないできる権限の定義を書けば式になる
どんな攻撃にも破られないできない「どんな攻撃にも」を式に書けない
ハードウェアの脆弱性も含めて安全モデルの外seL4 もハードウェアの正しさを前提にしている

言えるのは、「書いた種類のホールが、前提の範囲にはない」ことまでです。

決定できる論理と、できない論理

決定可能とは、式を渡すと、正しいか間違いかを必ず有限時間で答える手順があることです。扱えるかどうかの話ではありません。決定不能な論理でも、式は書けますし、証明もできます。自動で答えが出る保証がないだけです。どの論理が決定可能かは、次のように分かれます。

論理判定備考
命題論理（SAT）決定可能NP 完全（Cook, 1971）
整数の足し算（プレスブルガー算術）決定可能最悪の計算量は非常に大きい
実数の足し算と掛け算決定可能Tarski。計算は重い
実数に sin などを加える決定不能扱える場合は限られる
整数の足し算と掛け算決定不能ヒルベルトの第10問題（Matiyasevich, 1970）
一階述語論理決定不能Church と Turing, 1936。正しい式は証明を探せば見つかる

手元の実験（Z3、制限時間20秒）

式結果
3*a + 6*b == 1（整数、足し算だけ）unsat
x*x*x + y*y*y + z*z*z == 114（実数）sat
同じ式（整数）unknown（時間切れ）

同じ式でも、実数なら解けて、整数では解けません。整数は掛け算と組み合わせると計算そのものを式で表せるので、停止性問題と同じ壁にぶつかります。固定長の整数なら有限なので決定可能ですが、ビット数が増えると計算は重くなります。

Lean の論理は表現力が高いので、全体としては決定不能です。それでも、定理は自由に書けて、できた証明は機械的に検算できます。決定不能なのは「証明を見つける」部分で、そこを人や AI が担当します。

試したこと結果
x < y → x + 1 ≤ y を omega（線形の整数を解く命令）で自動で証明
x * y = y * x を omega で失敗（掛け算は対象外）
x * y = y * x に定理 Nat.mul_comm を渡す通過
コラッツ予想を定理として書く書ける。証明は sorry のまま

計算量：解けても終わらない

SAT は NP 完全です。P ≠ NP が正しければ（未解決の予想です）、最悪の場合に素早く解く方法はありません。現実の問題の多くが解けるのは、実際の式に構造があり、解法がそれを利用できるからで、難しい入力が消えたわけではありません。

ゲーデルの不完全性定理：証明する体系自身の限界

ここまでは計算の限界でしたが、不完全性定理は証明そのものの限界です。

  • 第一不完全性定理：一定の算術を含む無矛盾な形式体系には、その体系の中で証明も反証もできない文が存在します
  • 第二不完全性定理：そのような体系は、自分自身の無矛盾性を証明できません

検証にとっての意味は2つあります。第一に、公理を決めれば、その公理では届かない真理が残ります。公理を足せば、足した体系にまた新しい限界ができます。第二に、Lean のような証明支援系は、自分の論理が矛盾していないことを自分で証明できません。ある論理を信じる根拠は、より強い論理か、人の判断に頼ることになります。

ただし、これは普段のプログラム検証で直接ぶつかる壁ではありません。実務で止まる原因は、ほとんどが前述の計算量や、不変条件、仕様の書き方です。

形式化できないこと

最後の限界は数学の外にあります。形式検証は、形式の世界の中で正しさを示す技術です。「本当に欲しかったものは何か」を決める工程は形式化できません。使いやすいか、公平か、この仕様でよいのか、という判断は人に残ります。

まとめ証明が保証するのは「書いた性質が、書いたモデルで、前提の下で成り立つ」ことです。だからこそ、検証の価値は道具の選択より、何を性質として書くかで決まります。
